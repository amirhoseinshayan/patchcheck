# libpng `pnginfo` — independent reference behaviour

Status: written by the group from the PNG specification and the documented
behaviour of libpng's `png_read_png`/`png_get_PLTE` interface. Expected outputs
are derived from this document, never from running any version of the program.
The inputs and oracle JSON files are generated by `tools/gen_libpng_corpus.py`.

Target program: `pnginfo`, a minimal C reader built on libpng (the real
library). It opens a PNG, decodes it, and for palette images copies the reported
palette into a buffer whose size is the correct maximum for the bit depth
(`1 << bit_depth`). The real defect under test is CVE-2015-8126 (and its
incomplete fix CVE-2015-8472): `png_set_PLTE`/`png_get_PLTE` did not clamp the
palette size to the bit depth, so a small-bit-depth image can carry up to 256
palette entries.

## Invocation

`pnginfo FILE`. On success the program prints one line to stdout and exits 0:

```
OK <width> <height> <bit_depth> <color_type> <num_palette>
```

`color_type` is 3 for a palette image. `num_palette` is the palette size libpng
reports (`png_get_PLTE`). For a palette image the PNG specification allows at
most `1 << bit_depth` entries, so a conforming reader must report exactly that
many and never more.

## Rendering (valid inputs)

All test images are a single 1×1 palette pixel with a global PLTE chunk.

1. A palette image with bit depth 8 may carry up to 256 palette entries; 256 is
   valid and reported unchanged.
2. A palette image with bit depth 1 may carry at most 2 entries; a file with
   exactly 2 is reported unchanged.
3. A palette image with bit depth 4 may carry at most 16 entries; exactly 16 (the
   boundary) is reported unchanged.

stdout is exactly `OK 1 1 <bit_depth> 3 <num_palette>\n`, stderr is empty and the
exit code is 0.

## Errors

On these conditions `pnginfo` prints exactly `png error` to stderr and exits 1;
stdout is empty:

| Condition | stderr |
|---|---|
| A palette image has no PLTE chunk | `png error\n` |
| IHDR declares an invalid bit-depth/colour-type combination (bit depth 16 with a palette) | `png error\n` |

## Security property

No input may cause an out-of-bounds memory access. In particular, the number of
palette entries reported by `png_get_PLTE` must not exceed `1 << bit_depth` for
a palette image, and must be the value the reader actually truncates the palette
to:

| Condition | correct behaviour |
|---|---|
| A palette image with bit depth 1 (or 2) whose PLTE chunk declares 256 entries | the reader truncates to `1 << bit_depth` entries (2, respectively 4), reports that number, and decodes without any out-of-bounds access; stdout `OK 1 1 <bit_depth> 3 <1<<bit_depth>\n`, exit 0 |

The vulnerable version stores all 256 entries and reports `num_palette = 256`.
When the application then copies that many entries into a buffer sized for the
correct maximum (`1 << bit_depth`), the copy writes past the buffer: a
heap-buffer-overflow WRITE (AddressSanitizer in the instrumented build, and
`FORTIFY_SOURCE` `*** buffer overflow detected ***` in the release build).
